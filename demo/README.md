# The AgentChecksum walkthrough

A five-minute, offline, deterministic demonstration of what AgentChecksum is for. It uses
the real CLI, two local fixture servers from [`examples/`](../examples), and no cloud
account, no API key, and no network.

```bash
./demo/run.sh
```

From a clean clone the first run compiles the CLI and the fixtures, which takes a few
minutes. Every run after that is seconds.

## What it shows

The demo builds a small agent — a system prompt, a model endpoint, and a real MCP server
that declares one search tool — then walks it through the two questions the product
answers.

| Step | Command | What you see |
|---|---|---|
| 1 | `snapshot` | The agent is fingerprinted: a prompt, a model, an MCP server and the tool contract it declares |
| 2 | `diff` | A tool *description* changes while its input schema does not — reported as MEDIUM behavioral risk, because an API that did not break can still change what a model does |
| 3 | `check` | **Drift**: behavior was measured, but nothing has been accepted yet, so there is nothing to compare it with |
| 4 | `check --accept` | The measured behavior becomes the committed baseline |
| 4b | `check` | **PASS**: the same run, compared against what was accepted |
| 5 | `check` | **FAIL, exit 1**: the same endpoint starts answering differently, and the model calls a tool a probe told it not to call |
| 6 | `check --trace` | The **same FAIL**, replayed from recorded evidence with the model server stopped — no request, no endpoint, same verdict |

The interesting part is step 5. Nothing about the dependency state changed: the agent
checksum, the lockfile, the probe suite and the tool catalog are all identical. Only the
behavior moved, and it moved in a way no schema comparison could see. That is what the
Behavior Gate is for.

Step 6 is the other half of the promise: a verdict is a pure function of recorded
evidence, so it can be reproduced later, on another machine, with no model running. The
evidence is bound to the agent it describes — replaying it against a different agent,
catalog, probe suite or runner is refused with exit 3 rather than scored.

## What the demo creates, and where

Everything happens in a temporary directory that is removed on exit. Nothing is written
into this repository, and nothing is left behind in your project.

The generated project looks like a real one, and its state is worth knowing about because
two of these paths are meant to be committed and two are not:

```text
agentchecksum.toml          source contract, committed
probes/                     source contract, committed
agentchecksum.lock          generated by `snapshot`, committed
.agentchecksum/baseline.json  generated by `check --accept`, committed
.agentchecksum/cache/       machine-local, gitignored — holds raw model samples
.agentchecksum/runs/        machine-local, gitignored — holds traces and evaluations
```

The demo also writes a `.gitignore`-respecting git repository inside the temporary
directory, because that is the workflow: the lockfile and the accepted baseline are
reviewed changes, not build output.

## If you want to take it apart

The two fixtures are ordinary example binaries and can be run by hand:

```bash
cargo build --example mcp_fixture_server --example openai_fixture_server
```

`mcp_fixture_server --stdio` speaks MCP and declares the tools in the JSON spec named by
`AC_FIXTURE_SPEC`; `openai_fixture_server` speaks the OpenAI chat-completions contract and
serves the responses in its own spec, one per request, repeating the last. Both write the
ephemeral port they bound to the file named by `AC_FIXTURE_PORT_FILE`. They are the same
servers the integration test suites drive, so what the demo shows is what the tests
assert.
